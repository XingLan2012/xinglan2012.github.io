博客原本只有一套界面：暗色、金调、碎星。

它不算惊艳，但足够稳 —— 没有依赖，打开就能读，任何浏览器都不挑。这份「稳」后来变成了一个约束：我想再要一套界面，一套立体的、会动的、像终端一样的界面，但它**不能取代原来那套**。因为三维意味着 WebGL，而 WebGL 意味着「在有些设备上就是打不开」。

于是有了这篇文章要讲的事：给博客接上第二套界面，默认那套一点不动，左上角放一个设置入口，想进的人自己进去。

现在它长这样：<https://xinglan2012.github.io/rhine/>

---

## 一、先想清楚：第二套界面是谁

第二套界面不是我画的。它是一个现成的开源项目 —— [RhineLabUI](https://github.com/LBEILC/RhineLabUI)（MIT，© 2026 LBEILC），一个用 TypeScript + Three.js + Vite 写的「交互式三维研究档案终端」：五列档案阵列、可以抽取翻转的卡片、磨砂玻璃外壳、旋转拆解的模型查看器，还有一整套启动动画与音效。

我做的不是重画，是**接进来，然后换内容**。

原则很早就定下了：**三维、动画、加载逻辑一律不动**。它们是这个项目的灵魂，动一处就要重新验证十处。我要动的只有两样 —— 内容数据，和入口。

## 二、只换数据，不碰代码

这个项目最讨人喜欢的地方，是它把内容单独放在一个 JSON 里：

```json
{
  "categories": ["…五个分类…"],
  "columns":    ["…三维阵列的列顺序…"],
  "records":    [ /* 四十份档案 */ ]
}
```

每条档案有编号、标题、中英名、科室、编目范围、相关人物、访问范围、摘要、若干条研究记录，以及一个原文链接。构建时脚本会校验它 —— 五列、每列八份、编号必须从 X-001 连续到 X-040。

于是「换内容」变成了一件很干净的事：把博客的东西编成四十条。

| 分类 | 内容来源 | 条数 |
| --- | --- | --- |
| 算法档案 | OIer 笔记（ST 表 / 树状数组 / 线段树 / 动态开点 / 并查集 / MST / 最短路 / Tarjan） | 8 |
| 数理档案 | 《Minecraft 哲学的数学原理》各章 | 8 |
| 站点手记 | 博客自己的页面（欢迎帖、关于、云盘、相册、时运……） | 8 |
| 指令档案 | Minecraft Java 26.2 指令参考 | 8 |
| 资源档案 | Mindbook 文档、云盘文件、相册照片 | 8 |

摘要与研究记录都是从原文里提炼的，最后那条链接则指回原文本身 —— 在终端的详情页里，它写着「原文 ↗」，点开就是博客里对应的那篇 md 或那个页面。

四十份档案，正好是博客的全部家当。

## 三、从 30 MB 到 10 MB

接进来第一版，产物 **30 MB**。首页要下三十兆，这不是「有点慢」，这是不可用。

### 字体：18.8 MB 里只用得到 0.5 MB

四个字重的 MiSans，每个 4.7 MB —— 因为里面装着整个中文字库，两万个字形。而这个终端实际会显示的字，数一数：

**1239 个。**

那就裁。收集界面文案与四十份档案里出现过的全部字符，加上 ASCII、中文标点、全角形式作为余量，把四个字重各裁一份：

```
MiSans-Light.woff2     4698 KB → 131 KB
MiSans-Regular.woff2   4745 KB → 129 KB
MiSans-Demibold.woff2  4877 KB → 131 KB
MiSans-Bold.woff2      4962 KB → 132 KB
合计：18.8 MB → 0.51 MB（省 97.3%）
```

渲染结果完全一样，裁掉的只是用不到的字形。唯一的代价是：将来若新增生僻字，那一个字会回退到系统字体显示 —— 不会破版，只是那一个字不是 MiSans。

### Service Worker：首访慢的真凶

体积砍完还是慢，于是我读了一遍它生成的 `sw.js`，发现了这个：

```js
await cache.addAll(urls.map(url => new Request(url, { cache: "no-cache" })));
```

它把 **62 个文件、28 MB** 一次性塞进离线缓存，而且用 `cache: "no-cache"` **强制绕过 HTTP 缓存重新下载**。

也就是说：首次访问，你先把 30 MB 下一遍给页面用，紧接着 Service Worker 再原样下 28 MB 存起来。整站被下了两遍。

按这个项目自己的说明，离线能力是为「从主屏幕打开」准备的。但对一个放在博客里、随时联网可用的页面来说，这笔账不划算。于是我把预缓存收窄成**只缓存外壳** —— HTML、JS、CSS、档案文本、图标，一共 **1 MB**；字体、模型、音频改为在线按需加载。

```
预缓存：62 个文件 / 28 MiB  →  50 个文件 / 1.0 MiB
```

### 一次失败的尝试：模型量化

模型两个，一共 6.6 MB，是仅次于字体的第二块。我用 `gltf-transform` 做了 `weld + quantize` —— 把顶点、法线、UV 压成 16 位，体积掉到 4.5 MB，压缩率 32%，而且不需要 Draco/Meshopt 解码器，Three.js 原生就认。

数字很好看。**然后你告诉我：新开浏览器重新加载，看着很诡异。**

你是对的。问题出在法线：量化到 16 位之后，磨砂玻璃外壳的折射与高光表现变了。那些细节本来就靠着精细法线在撑，压掉精度，质感就塌了。我之所以没发现，是因为我的浏览器缓存里还是**原始模型**，直到清缓存才看得见差别。

已全部还原，并逐一核对 MD5 与原始文件一致。这条教训我记下了：**几何数据的「无损压缩」并不无损 —— 对靠法线吃饭的材质，它就是有损的。**

最终体积：

| 项目 | 原始 | 现在 |
| --- | --- | --- |
| 字体 ×4 | 18.8 MB | 0.5 MB |
| 模型 ×2 | 6.6 MB | 6.6 MB（保持原始） |
| 音频 | 3.0 MB | 1.6 MB（移除未引用的预览文件） |
| JS + CSS | 1.0 MB | 1.0 MB |
| **合计** | **30 MB** | **10 MB** |

速度这件事，能省的省，不能省的就不省。

## 四、让等待看得见

体积合理了，但首屏仍要下几个兆。等待最怕的不是久，是**不知道还要多久** —— 一片黑屏最容易让人以为它坏了。

所以做了三件事。

### 进度条的分母要对

进度条最忌讳「走到 99% 卡住」。所以分母只算**真正阻塞启动的资源**：脚本、样式、字体，加上场景 `load()` 明确等待的那个阵列模型 —— 7 个文件，4.8 MB。

详情页那个更大的装配模型是启动**之后**才下载的，不计入。这样进度到 100% 的那一刻，正好就是可以开始看的那一刻。

### 真实字节，而不是估算

只靠「资源加载完成」事件来推进度，会看到 `0% → 30% → 100%` 这种三级跳 —— 因为一个大模型占了七成的等待，而它只在结束时汇报一次。

我想要的是一格一格地走。做法是包一层 `fetch`，把响应体**分流**：

```js
const branches = response.body.tee();
consume(branches[0], rel);              // 一条用于计数
return new Response(branches[1], …);    // 一条原样交给应用
```

`ReadableStream.tee()` 把流一分为二，应用照常拿到完整数据，我在这边收一片数十片地累加真实字节。**不会产生第二次下载**，也不是估算 —— 分片到多少，进度就是多少。

配合两个刷新机制：分片到达即时绘制（合并到动画帧），另有一条 120 ms 的固定节拍兜底（浏览器节流 `requestAnimationFrame` 时仍然刷新）。

限速 250 KB/s 下的实测：进度值变化次数从 **4 次变成 37 次**，19% 到 99% 连续推进。

### 没有 WebGL 时，不要黑屏

这是最初的问题：这台设备打不开第二套界面，屏幕上什么都没有。

原因很直白 —— WebGL 上下文创建失败时，Three.js 抛错，而这个项目当时没有兜底界面，于是画面就停在最初的黑色上。

现在的行为是：**进入前先检测**，不支持就在设置里把入口置灰并说明；**即使进去了才失败**，也会显示一段说明和一个「返回博客」的入口。

宁可说清楚「这里进不去」，也不要让人对着黑屏猜。

## 五、踩坑清单

写下来，免得下次再踩：

1. **默认分支是 `master`，而直链写的是 `/main/`。** 云盘的下载链接 404 了很久才发现。修的时候顺手全库排查了一遍。
2. **`github.com` 被限速，`api.github.com` 却正常。** 推送反复失败：`GnuTLS recv error (-110)`、传输速率不足 1 KB/s。最后用 HTTP/1.1 + 关闭低速中断的耐心模式推成功。这两个域名的可达性是可以分开的。
3. **Service Worker 会缓存 `index.html`，把测试骗过去。** 我改了页面，测试却始终读到旧版，查了很久才发现是导航回退缓存。测试这类站点必须用全新 profile 或先禁用缓存。
4. **构建注入的判重条件不能拿变量名。** 我写了一行判断「页面里是否已有内联清单」，用的却是清单变量名 —— 而**读取该变量的代码本身**就含这个字符串，于是永远判定「已注入」，注入从未发生（一直靠兜底文件撑着）。
5. **只挂 `requestAnimationFrame` 的渲染不可靠。** 后台标签页里 rAF 会被节流甚至暂停，进度条就再也不动了。固定节拍兜底是必要的。

## 六、命名

第二套界面原本是别人的名字。既然要长期挂在博客上，就得改。

但**不能全改成一个名字** —— 那读起来会很怪。所以做的是一套**系列**，各司其职：

- **XINGLAN LAB** —— 机构，出现在品牌行、页脚、弹窗抬头
- **XINGLAN·LAB** —— 标记，Logo 与启动动画里逐字键入的那个
- **XINGLAN OS** —— 系统，页面标题与档案抬头
- **XINGLAN LAB.LLC.** —— 法人，欢迎页那句
- 中文则用 **星澜实验室** 与 **星澜之境**

装配结构里的六个部件也给了系列代号：`XL·FST` 紧固件、`XL·COV` 透明盖板、`XL·RNG` 折射环组、`XL·COR` 光学核心、`XL·SUB` 信息基板、`XL·FRM` 背板与框架。

有两处旧名字我**故意留着**：Service Worker 与页面之间的内部协议常量，改了会让「新版页面 + 旧版缓存」过渡期的更新按钮静默失效；还有模型文件内部的节点名 —— 改它就要重新处理模型资产，而这正是前面翻过车的地方。

## 结语

现在，博客有两套界面。

默认那套，仍旧是暗色、金调、碎星，谁都能打开。左上角多了一个齿轮，点开是「XinglanOS 终端」；进去是四十份档案，五列立体的卡片，可以抽取、翻转、拆解，看完按返回键回到博客。

四十份档案里装的，就是这个博客本身的全部内容 —— 那些算法笔记、那本关于 Minecraft 的书、那些写下来的话。

一套界面负责让人**读得到**，另一套负责让人觉得**值得走进去**。

而我最满意的地方，是那四十条档案的最后一行，写着「原文 ↗」。无论终端做得多花哨，点下去，它总归会把人送回文字本身。

循此苦旅，终抵繁星。
